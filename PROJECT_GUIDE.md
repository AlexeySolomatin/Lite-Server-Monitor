# 1. Речь для первых 30 секунд (elevator pitch)

Lite Server Monitor — это легковесная система мониторинга Linux-серверов,
написанная на Bash. Она не требует Docker, баз данных и веб-интерфейса:
устанавливается одним скриптом, ставит systemd-таймеры, которые по расписанию
запускают модули проверки (диски, SMART, RAID, температура, память/CPU,
SSH-входы, Fail2Ban, Docker, ИБП), и отправляет уведомления в Telegram или
на почту при проблемах, с защитой от спама и recovery-сообщениями.

Целевая аудитория — домашние и небольшие офисные серверы, где Zabbix или
Prometheus избыточны. Философия: «установил → настроил → забыл».

Ключевые цифры для уверенности:
- 10 модулей мониторинга + 1 системный (core);
- ~85 shell-скриптов, всё на Bash 5 (Ubuntu/Debian);
- единый контракт модулей, единый канал уведомлений, единый стиль логов.

# 2. Почему Bash, а не Python/Go (спросят обязательно!)

Готовый ответ:
1. Bash есть на любом Linux-сервере — **ноль зависимостей** для запуска,
   мониторить можно даже «голую» систему;
2. Задача — вызов системных утилит (df, smartctl, systemctl, journalctl) и
   разбор их вывода — это родная территория shell;
3. Легко диагностировать и чинить вручную: администратор может открыть
   любой файл и понять, что происходит, без знания языка проекта;
4. Минимальное потребление ресурсов: скрипт отрабатывает и выгружается,
   ничего не висит в памяти.

Честно признать минусы (это плюс на собеседовании): строгая обработка ошибок
в bash требует дисциплины (`set -Eeuo pipefail`, ручная проверка кодов
возврата), нет типизации, тестировать сложнее. И добавить: «поэтому мы ввели
единые контракты и библиотеки-обёртки, чтобы модули писались одинаково».

# 3. Архитектура: слои и потоки данных

```
 Пользователь
     │  lsm <команда>
     ▼
 bin/lsm  ────────────────► маршрутизация команд (case + exec)
     │
     ▼
 commands/*.sh ───────────► реализации команд (status, report, doctor...)
     │
     ▼
 lib/core/*.sh ───────────► «стандартная библиотека»: логи, UI, Module API,
     │                       отчет, конфиг
     ▼
 lib/notifications/*.sh ──► единый диспетчер уведомлений (notify → Telegram/Email)
     ▲
 modules/<name>/ ─────────► 10 независимых модулей мониторинга
     │                       каждый = manifest + install/uninstall + check-скрипт
     │
 systemd (timers) ────────► запускают check-скрипты по расписанию
```

Установка — отдельный поток:
```
 bootstrap.sh → installer/install.sh → wizard (интерактив) → steps/01..08
```
Обновление: `lsm update` → скачать tarball кода → применить → установщик в
тихом режиме `--update` (без вопросов, конфигурация и модули сохраняются).

**Главная идея, которую нужно донести:** модуль — это плагин с контрактом.
Ядро (Module API) не знает, что проверяет модуль; оно знает только, как его
запустить и как интерпретировать код выхода. Добавить новый мониторинг =
создать каталог с 4-5 файлами, не трогая ядро.

# 4. «Классы» в bash-проекте: каталоги и библиотеки

В bash нет классов — роль классов играют **библиотеки-файлы** (подключаются
через `source`) и **каталоги-компоненты**. Ниже полная карта.

## 4.1. bin/lsm — точка входа (аналог main())

| Функция | Что делает |
|---|---|
| `bootstrap_error` | Аварийный вывод до загрузки библиотек |
| `ensure_root` | Если не root — перезапускает себя через `exec sudo`, сохраняя команду и аргументы |

Маршрутизация: `case "${COMMAND}" in ...` для каждой команды делает
`exec bash "${LSM_ROOT}/commands/<имя>.sh" "$@"`. `exec` заменяет процесс —
нет лишнего слоя bash.

## 4.2. commands/*.sh — команды CLI

| Файл | Назначение |
|---|---|
| `status.sh` | Компактный статус: сервер, каталоги, модули одной строкой, таймеры |
| `report.sh` | Генерация отчета; флаги `--save`, `--send` |
| `doctor.sh` | Самодиагностика: права, каталоги, systemd, модули, Docker; итог «Ошибок/Предупреждений» |
| `modules.sh` | Управление модулями: list/available/install/remove/status/enable/disable |
| `config.sh` | Просмотр конфигов (`list`, `show <файл>`) |
| `update.sh` | Тихое обновление: скачать код → установщик `--update` |
| `install/uninstall.sh` | Обертки над установщиком |
| `help.sh`, `version.sh` | Справка и версия (версия читается из файла VERSION) |

## 4.3. lib/core/ — стандартная библиотека ядра

| Файл | Роль | Ключевые функции |
|---|---|---|
| `logging.sh` | Единое журналирование | `log_error/log_fail/log_warn/log_success/log_info/log_debug` (внутри `_log_parse_args`, `_log_write`); уровни: ERROR=0 … DEBUG=3; пишет и в консоль, и в файл `/var/log/lsm/lsm.log` |
| `colors.sh` | Единственное место с ANSI-кодами | переменные `COLOR_*`; при не-TTY и `NO_COLOR` — пустые |
| `ui.sh` | Терминальное оформление | `ui_banner` (ASCII-логотип), `ui_section` (заголовки секций) |
| `module_api.sh` | Контракт с модулями | см. раздел 5.2 |
| `report.sh` | Генератор отчета | `report_generate_full` (собирает всё), `report_get_header`, `report_get_system_metrics` (бары CPU/память/swap, таблица ФС), `report_get_active_alerts`, `report_bar` (визуальный индикатор), `report_collect_modules` |
| `common.sh` | Общие проверки окружения | `is_root`, `command_exists`, `is_supported_os`, `has_internet` |
| `config.sh` | Работа с /etc/lsm | загрузка конфигов |
| `checks.sh`, `filesystem.sh`, `utils.sh` | Утилиты | проверки ОС, файловые операции |

## 4.4. lib/notifications/ — единый канал уведомлений

| Файл | Роль |
|---|---|
| `notify.sh` | **Диспетчер**. Публичные функции: `notify <модуль> <OK\|WARNING\|CRITICAL> <текст>` (с throttle-логикой), `notify_info` (информационное, без state), `notify_raw` (прямая доставка, для ежедневного отчета) |
| `telegram.sh` | Доставка в Telegram Bot API (curl) |
| `email.sh` | Доставка через msmtp с SMTP-параметрами из конфига, fallback mail/mailx |

Ключевая логика notify() — раздел 5.4.

| Файл | Роль | Ключевые функции |
|---|---|---|

| `registry.sh` | Реестр модулей | `registry_scan` (читает modules/*/manifest.conf), `registry_resolve_order` (топологическая сортировка зависимостей), `registry_exists` |

| `packages.sh`, `permissions.sh`, `services.sh` | apt, права, юниты | вспомогательные |

## 4.6. installer/ — сам установщик

- `install.sh` — оркестратор: определяет интерактивный/авто/`--update` режим,
  загружает библиотеки, запускает этапы по порядку из массива `STEPS`;
- `wizard.sh` + `screens/*.sh` — интерактивный мастер (режим, выбор модулей
  чек-листом, Telegram, SMTP, ИБП, ежедневный отчет, сводка);
- `steps/01..08` — этапы: окружение → пакеты → каталоги → конфигурация →
  модули → службы → права → финиш;
- `update.sh`, `uninstall.sh` — вспомогательные сценарии.

## 4.7. modules/<имя>/ — плагины мониторинга

Структура КАЖДОГО модуля (это и есть «класс» модуля):

```
modules/disk/
├── manifest.conf        # метаданные: MODULE_ID, CATEGORY, DEPENDENCIES, DEFAULT
├── install.sh           # ставит systemd-юниты, конфиг из шаблона, активирует таймер
├── uninstall.sh         # симметрично удаляет всё, включая state
├── files/
│   ├── check_disk.sh    # ВЕСЬ интеллект модуля: режимы status|report|check
│   ├── lsm-disk.service # oneshot-служба, запускающая check-скрипт
│   └── lsm-disk.timer   # расписание (OnCalendar)
├── templates/disk.conf  # шаблон конфига → /etc/lsm/modules/disk.conf
└── README.md            # документация модуля
```

Список модулей (по одной строке — расскажите любой):

| Модуль | Что делает | Источник данных |
|---|---|---|
| disk | заполнение всех ФС, бары в отчете | `df -P` + awk-фильтр псевдо-ФС |
| smart | здоровье и температура дисков | `smartctl -H` (код возврата), `-A` (атрибуты 194/190) |
| raid | целостность md-массивов | `/proc/mdstat` |
| system | load average, память | `/proc/loadavg`, `/proc/meminfo` |
| temperature | CPU/чипсет (диски — у smart) | `sensors` с фолбэком `/sys/class/thermal` |
| ups | ИБП APC | `apcaccess` (нет утилиты → корректный пропуск) |
| docker | демон, контейнеры, объем | `docker ps`, `docker system df` |
| login | входы по SSH | `journalctl` + дедупликация по хэшам |
| fail2ban | баны по jail | `fail2ban-client` + diff с прошлым списком |
| core | системный: ежедневный сводный отчет | ставит `lsm-report.service/.timer` |

# 5. Ключевые механизмы «как это работает»

## 5.1. Контракт модуля (Module API) — главная идея проекта

`lib/core/module_api.sh`. Каждый check-скрипт обязан принимать **режим
позиционным аргументом** и возвращать осмысленный код:

| Режим | Что делает | Код выхода |
|---|---|---|
| `status` | краткий статус для CLI | всегда 0 |
| `report` | человекочитаемый отчет | всегда 0 |
| `check` | машинная проверка + уведомления | 0=OK, 1=WARNING, 2=CRITICAL/ошибка окружения |

Функции API: `module_api_list_installed` (по маркерам в
`/var/lib/lsm/modules/*.installed`), `module_api_run` (запуск), `module_api_check`
(проверка кода), `module_api_report_all` / `module_api_check_all` (циклы по
модулям), `module_api_is_system` (системные модули вроде core не имеют
check-скрипта — и это НЕ ошибка).

Благодаря контракту `lsm doctor` просто запускает `check` у всех модулей и
интерпретирует коды — ядро не знает деталей.

## 5.2. Реестр и зависимости

`modules/<name>/manifest.conf` — плоский файл `KEY="VALUE"`. Реестр
(`registry.sh`) сканирует каталоги, делает `source` манифеста через
`module_load_manifest` и складывает метаданные в **ассоциативные массивы**
(`declare -A LSM_MODULE_NAME` и т.д.). `registry_resolve_order` строит
порядок установки с учетом `MODULE_DEPENDENCIES` (все мониторинговые зависят
от core; core — системный модуль, зависит ни от кого).

## 5.3. Схема «service + timer» systemd

Каждый модуль — пара юнитов:
```
lsm-disk.timer  (OnCalendar=*:0/5)  →  lsm-disk.service (Type=oneshot)
                                            → check_disk.sh check
```
Важный опыт из эксплуатации: таймеры делали монотонными (OnBootSec/
OnUnitActiveSec) — после обновления юнитов поверх активных таймеров и
daemon-reload они переставали планироваться (NEXT = «-»). Перешли на
календарные `OnCalendar` + `Persistent=true`: переживают простой сервера и
перезагрузки. Это отличный рассказ для собеседования: «поймали в бою,
поняли механизм, исправили с обоснованием».

Управление: `lsm modules enable/disable` = `systemctl enable --now` /
`disable --now` таймера. Имена: `lsm-<модуль>.timer`, исключение —
модуль core ставит `lsm-report.timer`.

## 5.4. Уведомления и защита от спама (throttling)

`notify <module> <LEVEL> <message>`:
1. state-файл `/var/lib/lsm/state/<module>.state` хранит
   `<timestamp>|<LEVEL>`;
2. первый алерт — отправляем и пишем state;
3. повторный в течение `ALERT_COOLDOWN` (3600с) — молча подавляем;
4. эскалация WARNING→CRITICAL — отправляем немедленно, минуя кулдаун;
5. `notify <module> OK` — если state существовал, отправляем
   🟢 RECOVERY и удаляем state (проблема ушла);
6. `notify_info` — информационные события (успешный SSH-вход) без
   alert-семантики; `notify_raw` — всегда-доставка (ежедневный отчет).

Диспетчер рассылает во все включенные каналы (`TELEGRAM_ENABLED`,
`EMAIL_ENABLED` в config.conf). Секреты — отдельно в `secrets.conf`
(600, root:root). Это классический паттерн **изоляции секрета от кода**.

## 5.5. Установка и обновление

`bootstrap.sh` скачивает код, установщик проходит 8 этапов. Модули выбираются
интерактивным чек-листом (цифра — toggle `[ ]`/`[X]`, 0 — подтверждение,
экран перерисовывается `clear`, есть fallback для не-TTY).

Повторная установка **идемпотентна**: конфиги не перезаписываются
(создаются только если отсутствуют), секреты сохраняются.

`lsm update`: скачивает архив кода из GitHub, заменяет только каталоги с
кодом (bin, commands, installer, lib, modules, templates), запускает
установщик с `--update` — тот берет список модулей из state-маркеров и
не задает ни одного вопроса. Скрипт обновления имеет резервные реализации
(log-функций), чтобы обновиться даже на поломанной установке.

## 5.6. Дисциплина bash (частые вопросы интервьюера)

`set -Eeuo pipefail`:
- `-e` — немедленный выход при любой ошибке;
- `-E` — ERR-trap наследуется в функции/под-оболочки;
- `-u` — ошибка при обращении к необъявленной переменной;
- `-o pipefail` — пайплайн возвращает код ПЕРВОЙ упавшей команды.

Знаем цену: под `-u` нельзя объявить `local x` и прочитать до присваивания
(поймали такой баг в мастере установки), под `-e` надо аккуратно писать
`cmd || rc=$?` для команд, чей ненулевой код — часть логики (smartctl).

Остальное:
- `flock` + дескриптор 200 — защита от параллельного запуска проверки;
- `LC_ALL=C` — стабильный парсинг вывода системных утилит;
- guard-файлы `[[ -f ... ]] && source` — библиотеки не роняют скрипты;
- защита от повторной загрузки библиотеки: `[[ -n "${LSM_..._LOADED:-}" ]] && return 0`.

# 6. Реальный опыт отладки (ваши истории для собеседования!)

Расскажите 1-2 из этих историй по схеме «симптом → гипотеза → эксперимент →
корень → фикс → профилактика»:

1. **«Тихий» mawk.** Симптом: doctor ругался на модуль disk с ошибкой
   `awk: unexpected newline`. Причина: gawk (в моем окружении) допускает
   перенос строки после `if (`, а mawk (awk по умолчанию в Ubuntu) — нет.
   Урок: **тестировать на целевой платформе, а не на своей**.

2. **Строковый LOG_LEVEL.** Симптом: у двух модулей `INFO: unbound variable`.
   Причина: конфиг задавал `LOG_LEVEL="INFO"` строкой, а арифметика bash
   `(( LOG_LEVEL < level ))` пыталась разрешить имя `INFO` как переменную.
   Фикс: нормализация строкового уровня в число перед сравнением. Урок:
   bash-арифметика небезопасна к типам, валидировать вход.

3. **Самокопирование файла.** Установка падала на первом же модуле:
   `cp: ... are the same file` — при установке из bootstrap-дерева источник
   и цель совпадали, `set -e` прерывал всё. Фикс: убрали лишнюю копию +
   guard `-ef` в deploy-функции. Урок: идемпотентность и защита на уровне
   библиотеки, а не конкретного вызова.

4. **Мертвые таймеры.** После переустановки 7 из 10 таймеров показывали
   NEXT = «-». Диагностика показала: они enabled/active, но не планировались
   — монотонные таймеры не переживают замену юнитов поверх активных.
   Решение: OnCalendar + Persistent. Урок: выбирать механизм по поведению
   при эксплуатации, а не по привычке.

5. **Замкнутый круг обновления.** `lsm update` умирал до `git pull` из-за
   бага в самом себе — не мог обновить сам себя. Фикс: резервные
   реализации функций в update-скрипте + смена механизма (tarball вместо
   git pull). Урок: команда обновления должна работать на самой деградировавшей
   системе.

6. **Дубли метрик.** Корень мониторили и system, и disk; температуры дисков
   могли прийти из smart и temperature. Ввели принцип «один владелец на
   метрику» и развели зоны ответственности. Урок: архитектурные правила
   появились из реальной боли, а не из книжки.

# 7. Тестирование и качество

- Смоук-тесты ad-hoc (около 50 проверок): каждая команда CLI, каждый модуль
  в трех режимах, синтаксис всех скриптов (`bash -n`), фейковые утилиты

- автobump версии по conventional commits (feat → минорная, fix → патч);
- документация как код: PROJECT_CONTEXT.md (архитектурные контракты),
  docs/AUDIT_AND_ROADMAP.md (аудит + план), README каждого модуля.

Честные ограничения (назовите сами — это плюс): пока нет каталога tests/ в
CI; часть багов была найдена живой эксплуатацией, а не тестами — поэтому
P0-задача в роадмапе это каркас автотестов.

# 8. Вероятные вопросы и короткие ответы

**Q: Почему exit-коды 0/1/2, а не 0/не-0?**
A: Гранулярность для диагностики: doctor может различить WARNING и CRITICAL.
Контракт зафиксирован в Module API и одинаков для всех модулей.

**Q: Как модуль отправляет уведомление?**
A: Никак сам. Он вызывает `notify` из центрального диспетчера. Ядро решает:
что слать (уровень), куда (включенные каналы), когда (кулдаун/эскалация/
recovery). Модули не знают про Telegram и SMTP вообще.

**Q: Что в state-файлах? Кто владелец?**
A: `<модуль>.state` — `timestamp|LEVEL`, владелец notify.sh; модули пишут
только свои рабочие кэши (например, хэши обработанных SSH-событий) и
lock-файлы. Владение явно задокументировано, чтобы не было конфликтов.

**Q: Как защитились от одновременного запуска проверки?**
A: `flock` на дескрипторе 200 с lock-файлом в /var/lib/lsm/state; занятый
лок = пропуск с информационным сообщением, а не ошибка.

**Q: Почему установка через systemd-таймеры, а не cron?**
A: Таймеры дают журналирование через journald, зависимости, `Persistent`,
единый способ включения/выключения и наблюдаются стандартными средствами
(`systemctl list-timers`). Cron не переживает выключенный сервер.

**Q: Как устроен чек-лист в терминале без ncurses?**
A: Функция рисует меню, читает цифру через `read`, переключает элемент
массива состояний и вызывает `clear` + перерисовку. Экран перерисовывается
полностью — нет накопления текста. Есть деградация: если stdin не TTY
(например, curl | bash), принимаются значения по умолчанию.

**Q: Как обрабатываются секреты?**
A: Отдельный файл secrets.conf с правами 600 root:root, код никогда не
содержит токенов, установщик только переносит значения из интерактивного
ввода в этот файл.

**Q: Что самое сложное в проекте?**
A: Дисциплина обработки ошибок в bash на 85 скриптах и предсказуемость
поведения при частичных сбоях (сеть недоступна, диск заполнен, systemctl
не отвечает). Решалось контрактами, едиными библиотеками и живыми
экспериментами на сервере.

**Q: Что бы вы переписали на другом языке?**
A: Если проект рос бы в сторону агрегации многих серверов и API — ядро на
Go/Python. Но для одного сервера bash-решение честнее: меньше зависимостей
и порог входа для администратора.

# 9. Словарик (чтобы говорить уверенно)

| Термин | Значение |
|---|---|
| идемпотентность | повторный запуск не меняет результат (повторная установка ничего не ломает) |
| throttling | подавление повторных уведомлений в течение кулдауна |
| эскалация | повышение уровня алерта (WARNING → CRITICAL) с немедленной отправкой |
| recovery | уведомление о восстановлении после алерта |
| topological order | порядок, при котором зависимости устанавливаются раньше зависимых |
| TTY | терминал; проверка `[[ -t 1 ]]` отличает интерактив от пайпа |
| oneshot unit | systemd-служба, которая запускается и завершается |
| state-файл | файл с состоянием между запусками (алерт был/нет, прошлые баны) |
| conventional commits | стиль коммитов feat:/fix:/chore: — на них завязан автobump версии |
| псевдо-ФС | виртуальные ФС ядра (proc, sysfs, efivarfs...) — не нужно мониторить |

# 10. Если спросят «а покажите код»

Самые выигрышные файлы для демонстрации:
1. `lib/core/module_api.sh` — компактный API + объяснение контракта;
2. `lib/notifications/notify.sh` — конечный автомат алертов в 140 строк;
3. `modules/disk/files/check_disk.sh` — эталонный модуль (режимы, бары,
   фильтр псевдо-ФС);
4. `bin/lsm` — маршрутизация и sudo-перезапуск;
5. `installer/steps/05_modules.sh` — установка модулей по порядку зависимостей.
