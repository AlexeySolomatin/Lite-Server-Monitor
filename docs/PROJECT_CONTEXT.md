----------------------------------------------------------
### 1. PROJECT IDENTITY
----------------------------------------------------------

Название:

    Lite Server Monitor (LSM)


Назначение:

    Легковесная модульная система мониторинга Linux-серверов
    с автоматическими проверками и уведомлениями.

Цель:

    SMB / small infrastructure monitoring.

Приоритеты:

        1. Надежность
        2. Простота сопровождения
        3. Предсказуемость поведения
        4. Минимум зависимостей
        5. Модульность


 LSM НЕ является:

    - enterprise monitoring системой;
    - заменой Zabbix;
    - заменой Prometheus;
    - тяжелой распределенной системой мониторинга;
    - агентом, требующим сложной серверной инфраструктуры.


----------------------------------------------------------
### 2. ARCHITECTURE PRINCIPLES
----------------------------------------------------------

Основные архитектурные принципы:

1. Простота важнее моды.

2. Bash выбран намеренно.

   Причины:

       - доступен практически на любом Linux-сервере;
       - минимальное количество зависимостей;
       - легко диагностировать;
       - легко восстановить вручную;
       - удобно использовать системные инструменты Linux.

3. Компоненты должны иметь четкую ответственность.

4. Каждый мониторинговый модуль отвечает только
   за собственную область проверки.

5. Уведомления должны быть централизованы.

6. Конфигурация отделена от кода.

7. Состояние системы хранится отдельно от исходного кода.

8. Существующие API должны переиспользоваться,
   а новые API создаются только при необходимости.

9. Не следует усложнять архитектуру без практической необходимости.

### 8. SPECIAL STATUS OF MODULE "core"
----------------------------------------------------------

Модуль:

      modules/core/

имеет специальное назначение.

Он зарегистрирован в Module Registry как:

      MODULE_ID="core"

и используется как зависимость большинством
мониторинговых модулей.

Однако он не является модулем мониторинга
в обычном смысле.

У него отсутствует:

      check_core.sh

Причина:

      core выполняет системную инфраструктурную функцию,
      а не мониторинг отдельного ресурса сервера.

В текущей архитектуре:

      core
          |
          +-- lsm-report.service
          |
          +-- lsm-report.timer

Модуль отвечает за установку и удаление
системного механизма формирования ежедневных
сводных отчетов LSM.

При этом остальные модули используют:

      MODULE_DEPENDENCIES="core"

Следовательно:

      core остается зарегистрированным модулем
      и участвует в dependency graph,

но:

      core не обязан иметь check-скрипт
      и не должен проверяться через стандартный
      мониторинговый check-контракт Module API.

Поэтому отсутствие:

      check_core.sh

не является ошибкой установки или целостности
модуля core.

Module API и doctor должны учитывать специальный
статус этого модуля.

Переименование или перенос:

      modules/core/

на текущем этапе НЕ производится.

Причина:

      имя "core" уже является частью dependency graph
      и используется в manifest.conf других модулей.

Текущая задача:

      1. документировать специальный статус core;
      2. сохранить существующий dependency graph;
      3. скорректировать диагностику doctor;
      4. исключить требование check_core.sh для core;
      5. не создавать фиктивный check-скрипт только
         для прохождения стандартной проверки.

### 10. MODULE API
----------------------------------------------------------

Основной API:

      lib/core/module_api.sh

Назначение:

      Единый интерфейс взаимодействия LSM
      с мониторинговыми модулями.

Поддерживаемые режимы:

      status
      report
      check

Контракт режимов (обязателен для всех мониторинговых модулей):

      status    Краткий однострочный статус. Всегда exit 0.

      report    Подробный человекочитаемый отчет. Всегда exit 0.

      check     Машинная проверка с уведомлениями:
                    0 = OK
                    1 = WARNING
                    2 = CRITICAL или ошибка окружения

Основные функции:

      module_api_list_installed()
      module_api_exists()
      module_api_path()
      module_api_get_check_script()
      module_api_run()
      module_api_status()
      module_api_report()
      module_api_check()
      module_api_report_all()
      module_api_check_all()
      module_api_is_system(MODULE)

module_api_is_system()

      Возвращает 0, если в manifest.conf модуля
      MODULE_CATEGORY="system".

      Системные модули (core):
          - не обязаны иметь check-скрипт;
          - пропускаются в report_all/check_all;
          - в doctor проверяются по специальному контракту
            (наличие каталога и manifest.conf).

Типовая модель мониторингового модуля:

      check_<module>.sh status
      check_<module>.sh report
      check_<module>.sh check

ВАЖНО: 

      Данный контракт применим к мониторинговым модулям.
      
      Он не обязан применяться к системному модулю core.

### 11. MODULE EXECUTION MODEL
----------------------------------------------------------

Мониторинговые модули работают через systemd.

Типовая схема:

      lsm-disk.timer
              |
              v
      lsm-disk.service
              |
              v
      check_disk.sh

Каждая проверка в общем случае:

      1. Загружает конфигурацию.
      2. Выполняет проверку.
      3. Определяет состояние.
      4. Обрабатывает уведомление.
      5. Обновляет состояние.

Конкретная реализация зависит от модуля.

### 13. STATE MODEL
----------------------------------------------------------

Состояние установки модулей:

      /var/lib/lsm/modules/

Пример:

      /var/lib/lsm/modules/disk.installed

Эти файлы используются для определения того,
установлен ли соответствующий модуль.


Runtime-state мониторинга (подтверждено):

      /var/lib/lsm/state/

Файлы:

      <module>.state
          Throttle-state уведомлений.
          Владелец — lib/notifications/notify.sh.
          Формат: <unix-timestamp>|<LEVEL>.
          Создается при алерте, удаляется при recovery.

      login_seen
          Хэши обработанных событий входа (модуль login).
          Формат: <timestamp>:<hash>, чистка записей > 10 минут.

      fail2ban_bans
          Кэш списка забаненных IP для diff-детекции
          (модуль fail2ban).

      smart_alert_<dev>
          Признак активного CRITICAL-алерта по диску
          (модуль smart).

      system.status
          Кэш последнего состояния модуля system.

      <module>_check.lock
          Lock-файлы защиты от параллельного запуска.

Правило:

      Модули НЕ пишут в <module>.state вручную.
      Этот файл принадлежит notify.sh.
      Собственные кэши модулей используют имена,
      не конфликтующие с <module>.state.

### 14. NOTIFICATION API
----------------------------------------------------------

Расположение (подтверждено):

      lib/notifications/notify.sh

Публичные функции:

      notify MODULE LEVEL MESSAGE
          Центральная функция алертов.
          LEVEL: OK | WARNING | CRITICAL.
          Ведет throttle-state /var/lib/lsm/state/<module>.state,
          кулдаун ALERT_COOLDOWN (по умолчанию 3600 секунд),
          поддерживает эскалацию WARNING -> CRITICAL.

      notify_info MODULE MESSAGE
          Информационное сообщение без alert-семантики.
          Не создает state и не участвует в кулдауне.
          Используется, например, для уведомлений
          об успешных входах (модуль login).

      notify_raw SUBJECT MESSAGE
          Прямая доставка готового сообщения в обход
          throttle-логики. Используется ежедневным отчетом
          (commands/report.sh).

Каналы доставки:

      lib/notifications/telegram.sh   Telegram Bot API
      lib/notifications/email.sh      msmtp (при заданном SMTP_SERVER)
                                      либо mail/mailx

Конфигурация каналов:

      /etc/lsm/config.conf             TELEGRAM_ENABLED, EMAIL_ENABLED,
                                       SMTP_*, ALERT_EMAIL / EMAIL_TO
      /etc/lsm/secrets.conf            TELEGRAM_BOT_TOKEN,
                                       TELEGRAM_CHAT_ID, SMTP_USER,
                                       SMTP_PASS

Правила:

      - все уведомления проходят только через notify.sh;
      - уровни ограничены OK | WARNING | CRITICAL
        (уровня INFO не существует);
      - check-скрипты модулей подключают notify.sh через source
        ([[ -f ]] guard), а не прямым исполнением.

### 18. UNINSTALL CONTRACT
----------------------------------------------------------

Главный установочный сценарий:

Он отвечает за orchestration удаления.

Модули:

### 23. CORE MODULE DECISION
----------------------------------------------------------

На текущем этапе принято решение:

      НЕ переносить modules/core/
      в другое место.

Причины:

      1. core присутствует в Module Registry.
      
      2. core является dependency
         для большинства модулей.
      
      3. Registry использует MODULE_DEPENDENCIES
         при разрешении порядка установки.
      
      4. modules/core/install.sh отвечает
         за установку lsm-report.service/timer.
      
      5. Переименование потребовало бы
         изменения dependency graph,
         registry и установщика.
      
      6. Практической необходимости
         в переносе сейчас нет.

Вместо этого:

      core остается системным модулем
      со специальным контрактом.

Следующий шаг:

      исправить doctor,
      чтобы он различал:
      
          monitor modules
      
      и
      
          system modules.
